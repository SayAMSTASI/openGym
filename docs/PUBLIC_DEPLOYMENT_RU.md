# Установка, владелец и передача прав

## Чистая установка Docker

```bash
git clone https://github.com/SayAMSTASI/openGym.git
cd openGym
cp .env.example .env
```

Для публичного домена измените в закрытом `.env`:

```dotenv
RP_ID=gym.example.com
ORIGIN=https://gym.example.com
WEB_PORT=8080
OWNER_SETUP=1
PASSWORD_LOGIN=1
INVITE_ONLY=1
ALLOW_GUEST=0
FIRST_USER_ADMIN=0
BOOTSTRAP_ADMIN=0
DEFAULT_LANG=ru
```

Подключите HTTPS reverse proxy к порту 8080. Не открывайте порт API напрямую.
Для проверки на том же компьютере исходный `.env.example` использует localhost.
Соберите именно эту версию из исходников:

```bash
docker compose up -d --build --wait
docker compose exec api cat /data/owner-setup-code
```

Последняя команда показывает секретный код только владельцу сервера. Он не
печатается в логах приложения и не входит в образ. Откройте сайт, выберите создание
профиля, введите собственные имя/пароль и этот код в поле кода владельца. Можно
также зарегистрировать passkey по HTTPS. При успешной регистрации профиль становится
администратором, а код расходуется навсегда. Посторонний без кода не сможет занять
место администратора, даже если откроет сайт раньше вас.

После этого уберите OWNER_SETUP=1 из `.env` или замените на 0 и пересоздайте API.
Маркер использованного кода сохранён в БД: рестарт, смена флага и передача прав
не открывают первоначальную настройку снова. Файл `data/owner-setup-code` можно
удалить после успешного входа. Регистрация остальных людей — по одноразовым
приглашениям из панели администратора.

Нет встроенного системного пользователя и одинакового для всех пароля. Код
владельца — временное доказательство доступа к серверу, а не пароль входа.

## Передача административных прав

1. Текущий администратор создаёт приглашение; будущий владелец регистрирует свой профиль.
2. Администратор открывает **Настройки → Аккаунт → Панель администратора → нужный пользователь → Передать права администратора**.
3. Проверяет имя и подтверждает действие своим паролем или passkey.

Получатель становится администратором, отправитель — обычным пользователем.
Записи обоих сохраняются. Нельзя передать права заблокированному пользователю,
профилю без способа входа или самому себе. Назначение и снятие прав выполняются
одним сохранением; операция заносится в журнал. Новый администратор может передать
права обратно. Если отправитель закреплён в ADMIN_UIDS, сначала уберите его ID
из этой переменной и перезапустите API — сервер не отменяет настройки владельца молча.

Если посторонний знает одноразовый код, он может занять установку. Не публикуйте код.
Если текущий администратор не сотрудничает, восстановление доступа выполняет
владелец сервера через закрытый `.env` (ADMIN_UIDS) по инструкции upstream.
Не удаляйте каталог data для сброса доступа: это уничтожает аккаунты и историю.

## Обновление существующей установки

Сделайте закрытую резервную копию `data/` и `.env`. Не копируйте их в GitHub.
Для установки с существующими пользователями OWNER_SETUP должен быть 0: настройка
первого владельца откажется стартовать поверх существующих аккаунтов. Текущие роли
сохраняются, а передача прав доступна действующему администратору. Старый механизм
BOOTSTRAP_ADMIN оставлен для совместимости с локальными установками; новая установка
его не включает. FIRST_USER_ADMIN также оставлен для совместимости и выключен
в опубликованных шаблонах.

## Секреты и публикация

В публичный репозиторий и Docker build context не входят `.env`, `data/`,
`coach-auth/`, `mcp/connection.local.json`, закрытые ключи, резервные копии и логи.
Реальные пользователи, приглашения, пароли, сессии и ключи MCP живут только в этих
закрытых файлах. В `.env.example` — лишь параметры и примеры доменов.

Проверка публичного дерева перед коммитом:

```bash
git add <нужные исходники>
node scripts/audit-public-source.mjs
```

Это проверка путей и распространённых форматов секретов, а не разрешение публиковать
любые произвольные пользовательские файлы. Не добавляйте личные данные в исходники,
задачи GitHub или скриншоты. Восстанавливайте установку с закрытой резервной копии;
чистая публикация исходников такую копию не заменяет.

Docker workflow можно запустить вручную в GitHub Actions. Образы относятся к
аккаунту владельца репозитория; до подтверждённого успешного запуска используйте
`docker compose up -d --build`, который собирает код локально.
